# 项目 01：内容框架草案

建议标题：IoT 设备控制模型的 Agent 迭代闭环

一句话：以 Claude Code 为决策中枢，结合子代理分工、受控执行脚本和文件化状态管理，串联问题诊断、样本构造、增量修复、评测、全量重训与模型部署上线，通过飞书回传结果，并将经验证的修复经验用于后续任务。

## 页面结构

1. **项目概述**：业务对象、输入与交付结果；在首屏标明个人职责。个人贡献沿用已有信息作为待核实项，不从系统文档推断全部模块的作者。
2. **背景与挑战**：IoT 自然语言到设备动作的解析任务；跨环节人工协调、业务知识分散、历史经验难复用。用一条匿名化设备控制示例帮助读者理解任务。
3. **系统如何完成一次迭代**：放主流程图。三类入口保留各自前置条件；主体围绕需要修复时的诊断—样本验证—增量训练—质量决策—全量重训与评测—模型部署上线—飞书报告展开；全量评测不通过则返回诊断。仅评测路线单独结束。
4. **三个关键设计**：① 主 Agent 保留选路和关键决策，子代理处理文档、数据与样本任务；② 结构化质量决策与受控脚本执行，配合校验清单、execution guard 和断点恢复；③ 业务规则、版本级运行状态、跨版本经验分离，索引按需加载，评测后再沉淀经验。
5. **一条案例与验证证据**：输入问题 → 诊断依据 → 修复动作 → 评测前后 → 是否进入全量重训。优先展示真实匿名案例、修复集结果、完整验证集与重点指标回归情况，再补人工操作次数和端到端耗时。没有记录的数字不写为成果。
6. **工程取舍与后续方向**：文件状态适合当前单机串行场景；增量修复先快速试错，全量重训验证整体效果；记忆写入保守以减少错误经验传播。区分已经实现与未来计划。

## 需要修正的旧文案

- 短期记忆不是易失的会话上下文，而是按版本保存的日志、评测记录与 lineage，支持恢复。
- 不能把“恢复”写成每次评测后的固定步骤；恢复是中断时的处理路径。
- 长期记忆写入不只是“评测通过”：还要求理解在最后一次人工纠正后稳定，必要时按新理解重新评测；只保留可复用经验。
- LangGraph 是设计借鉴，不应列为实际采用的框架。
- 项目文档存在“全程零人工确认”与“需复核/人工纠正”的不同描述，作品集应明确常规自动推进与例外介入。
- 概述中的修复阈值为 100%，脚本指南为 ≥99.9%，重点指标边界也有差异。最终以对应版本代码/运行记录核实；当前主图不列数值。
- “3–5 人、1–3 天”等属于文档中的背景描述，缺少对照记录时不据此计算提效比例。代码行数不作为主要成效。
